# 智能检测 Agent 项目面试问答

> 以下回答按照“核心开发”视角整理，请根据自己的实际参与范围调整。面试时先回答结论，再根据面试官追问补充细节，不需要一次把所有内容讲完。

## 1. 你在这个项目中主要负责什么？

**参考回答：**

我主要负责整体方案和核心功能落地，包括业务数据整理、计量和设备诊断结果接入、多轮问答、技术文档检索、报告与工单，以及安全作业模块的流程打通。我做得比较多的一点，是把原来相对独立的算法和数据能力整理成 Agent 可以安全使用的工具，并补上权限控制、评测和前端展示。

**可能追问：你认为自己最核心的贡献是什么？**

我认为是把“模型演示”做成了一个相对完整的业务闭环。系统不只是回答问题，还能找到数据、说明证据、生成报告，并在人工确认后创建工单。

## 2. 这个项目最难的地方是什么？

**参考回答：**

最难的不是接入大模型，而是保证它使用的数据可信。项目里有业务原始数据、算法结果、安防数据和技术资料，它们的字段、时间范围和统计口径都不一样。我花了比较多精力定义查询规则、数据边界和评测用例，防止 Agent 查错表、算错指标，或者把估算结果说成确定结论。

**可能追问：你是怎么解决的？**

我把不同数据源拆成独立的只读工具，并通过表白名单、字段说明、参考查询和自动评测来约束。复杂结论还会同时检查工具、参数、最终答案和数据来源。

## 3. 为什么不让大模型直接读取原始数据库？

**参考回答：**

因为原始数据库结构复杂，而且包含大量时序数据。让模型完全自由地查询，容易出现字段猜错、统计口径错误和越权访问。我给它提供的是受控查询入口，只允许访问白名单中的表，并限制查询类型、返回行数和执行时间。这样虽然自由度小一些，但结果更稳定，也更适合工业场景。

**可能追问：这样会不会限制 Agent 的能力？**

会有一定限制，但这是有意的取舍。业务系统更看重结果可验证，而不是让模型拥有无限操作能力。确实需要的新能力，可以通过新增受控工具逐步开放。

## 4. 如何降低大模型产生错误结论的风险？

**参考回答：**

我主要做了三层限制。第一层是数据事实必须通过工具查询，不能凭模型记忆回答；第二层是区分实测值、算法结果、估算值和模型解释；第三层是关键写操作需要人工确认。即使模型的解释有偏差，也不能修改底层诊断数值，更不能直接完成关键业务处置。

**可能追问：如果资料里没有答案怎么办？**

系统会明确说明没有找到足够证据，而不是用常识补一个答案。检索最多调整一次问题表达，再没有结果就停止。

## 5. 自然语言转 SQL 是怎么保证安全的？

**参考回答：**

系统不直接执行模型输出的任意 SQL。执行前会分析 SQL 结构，只允许单条只读查询，并检查表是否在白名单中。同时还有行数、结果大小和超时限制。业务库、诊断库和安防库也使用不同工具，避免模型跨边界访问数据。

**可能追问：SQL 写错了怎么办？**

工具会返回经过处理的错误信息。Agent 可以根据错误重写一次查询，但不能原样无限重试；第二次仍失败就如实告诉用户查询没有完成。

## 6. 如何保证用气量等业务指标不会算错？

**参考回答：**

这类指标不能只告诉模型一个字段名，还要固化业务口径。例如用气量需要先按企业、厂区和管路做五分钟平均，再进行积分，不能直接把原始分钟数据相加。我把这些规则写进查询说明和评测用例，并使用参考 SQL 核对结果。

**可能追问：为什么不能直接按用户汇总？**

因为不同厂区可能存在相同管路编号，直接汇总可能把不同实体混在一起。先保持正确的数据粒度，再向上汇总，结果才可靠。

## 7. 多轮对话的上下文是怎么保存的？

**参考回答：**

每个对话都有独立线程，消息、任务进度、工具结果和中断状态会持久化到 SQLite。用户再次进入同一对话时，可以继续追问；如果之前停在补充信息或工单确认，也能从原来的状态恢复。

**可能追问：不同用户之间会串数据吗？**

不会。系统使用用户编号和内部线程编号共同隔离对话，查询历史、附件和产物时也会校验所属用户。

## 8. 用户说“它”“刚才那个设备”时怎么处理？

**参考回答：**

Agent 会结合当前线程中的上一轮问题和结果，补全企业、设备或时间范围。例如上一轮查询了某个用户，下一轮问“它有哪些异常区间”，系统会沿用该用户，但仍然重新查询对应的异常数据，不会仅凭上一轮文字猜测。

**可能追问：上下文不明确怎么办？**

如果存在多个可能对象，而且不同选择会改变结果，就暂停并让用户明确；如果只是数据库返回零行，则直接说明无数据，不会反复追问。

## 9. 为什么要设计暂停和恢复，而不是直接让用户重新提问？

**参考回答：**

报告和工单经常需要补充企业、日期、优先级等条件。如果让用户重新开始，前面已经完成的查询和计划都会丢失。暂停和恢复可以保留当前状态，用户补充信息后继续执行，也为人工审批提供了统一机制。

**可能追问：哪些情况会暂停？**

主要有两类：缺少会影响结果的关键条件，以及创建工单前等待用户批准。普通的无数据或查询失败不会触发暂停。

## 10. 为什么创建工单一定要人工确认？

**参考回答：**

查询和分析是只读行为，但创建工单会改变业务状态，还可能影响现场人员安排。模型可以根据证据准备标题、优先级和检查清单，但最终是否创建应该由人确认，这样能避免误操作，也方便明确责任边界。

**可能追问：如何避免用户重复确认后产生重复工单？**

系统会根据来源、用户、标题和证据生成唯一标识。相同内容再次提交时会返回已有工单，而不是重复写入。

## 11. 自动生成的报告如何保证不是模型编出来的？

**参考回答：**

报告里的表格和图表必须引用已经执行成功的查询编号，图表字段也必须真实存在于查询结果中。模型不能手填一组数据去画图。报告正文还要求区分数据库事实、算法结果和模型解释，因此每个关键结论都能追溯到查询产物。

**可能追问：报告生成失败时怎么办？**

如果引用了不存在的查询或字段，工具会直接拒绝生成。Agent 需要修正数据来源，而不是生成一个看起来完整但无法追溯的报告。

## 12. 如果大模型、知识库或后端服务暂时不可用，系统怎么办？

**参考回答：**

不同故障会分开处理。知识库不可用时，系统会明确提示本次没有取得文档证据；数据库查询失败时不会编造结果；安全告警发送失败会先保存在本地，之后再重试。这样局部故障不会悄悄变成错误答案，也不会让重要事件直接丢失。

**可能追问：为什么告警要先落库再发送？**

因为平台可能暂时没启动或网络中断。先落库可以保留待发送记录，服务恢复后继续投递，可靠性比直接发一次请求更高。

## 13. 当前 Agent 响应比较慢，你会怎么优化？

**参考回答：**

从评测看，主要耗时不只是模型生成，还包括重复查询和过多工具调用。我会先减少不必要的查表，让一次查询尽量拿到完整数据；其次复用已有查询结果和诊断解读缓存；最后再根据任务复杂度选择不同模型，简单查询不必使用高成本推理。

**可能追问：你会优先看哪些指标？**

我会同时看首字时间、总耗时、模型调用次数和工具调用次数。只看总耗时很难判断问题是在模型、数据库还是流程设计上。

## 14. 如何控制大模型的调用成本？

**参考回答：**

首先只把完成任务需要的数据交给模型，不传大量原始时序数据；其次限制查询返回规模和工具调用次数；诊断解读使用内容和版本生成缓存标识，结果没有变化时可以直接复用。安全视频也只对候选事件调用一次大模型复核。

**可能追问：为什么不把所有任务都缓存？**

因为用户条件、现场补充信息和底层数据可能变化。只有输入、模型和流程版本都一致时才复用，避免拿旧结果回答新问题。

## 15. 你是怎么验证系统稳定性的？

**参考回答：**

项目既有单元测试，也有端到端评测。单元测试覆盖 SQL 安全、数据存储、流式输出、安全事件和 RAG 等模块；端到端评测则用真实数据库运行完整对话，检查工具选择、参数、回答、报告和人工确认流程。目前后端 97 项、前端 44 项自动化测试能够通过。

**可能追问：单元测试和 Agent 评测有什么区别？**

单元测试验证固定代码逻辑，结果应当稳定；Agent 评测验证模型在真实流程中的行为，会受到模型输出和服务状态影响，因此还要统计成功率、延迟和调用成本。

## 16. 为什么还要使用独立模型评审，规则判断不够吗？

**参考回答：**

工具名称、SQL 表和数字可以用程序直接判断，但“分析是否完整”“有没有过度推断”“是否清楚说明数据边界”很难只靠关键词判断。所以系统先做确定性检查，再用独立模型评审开放式回答。两部分都通过，任务才算成功。

**可能追问：模型评审本身可靠吗？**

它不是绝对标准，所以关键事实仍由程序和参考查询判断。模型评审主要补充表达质量和推理边界，并且它的调用和消耗会单独记录。

## 17. 项目目前有哪些明显不足？

**参考回答：**

第一，业务历史数据只有 19 天，暂时不能支持长期季节性分析；第二，部分设备退化轨迹是模拟数据，只能验证算法流程，不能当成真实生产效果；第三，Agent 自建评测集规模仍然较小；第四，目前安全作业主要处理本地视频，距离多摄像头实时部署还有差距。

**可能追问：为什么要主动说明这些限制？**

工业项目里错误地夸大结论风险很高。把数据边界说清楚，反而能说明我知道系统在哪些条件下可信，也知道下一步应该补什么。

## 18. 如果数据量扩大十倍，系统需要改什么？

**参考回答：**

我会先拆分在线查询和离线计算。大量时序数据提前生成日级汇总和诊断结果，Agent 优先查询整理后的数据，而不是每次扫描明细。文档检索可以继续按文档类型和版本增加过滤。服务层再补充任务队列、并发限制和更完整的运行监控。

**可能追问：是不是马上要更换数据库？**

不一定。先根据实际瓶颈判断，是扫描慢、并发不足还是网络调用慢。能通过分区、预聚合和缓存解决时，没有必要仅因为数据增长就重做全部存储。

## 19. 如果要把项目真正部署到生产环境，还缺什么？

**参考回答：**

除了扩充真实数据和现场验证，还需要完善权限分级、密钥管理、服务监控、数据备份、模型版本回滚和告警机制。算法结果也要和现场人员建立反馈闭环，持续记录误报、漏报和实际处置结果，才能判断系统是否真正产生业务价值。

**可能追问：你会如何灰度上线？**

先以只读和建议模式运行，不自动创建业务动作；选少量用户和设备与人工结果对比，确认稳定后再逐步开放报告、工单等能力，关键写操作仍保留人工确认。

## 20. 如果重新做一次，你会优先改进什么？

**参考回答：**

我会更早建立评测集和统一的数据口径。项目后期发现，很多 Agent 问题并不是模型能力不足，而是字段说明、工具边界和成功标准不够明确。如果一开始就用典型问题定义参考答案、允许工具和性能目标，后续选模型、设计工具和做优化都会更有依据。

**可能追问：这个项目让你最大的收获是什么？**

最大的收获是认识到，业务 Agent 的核心不只是提示词，而是可信数据、受控工具、状态管理、人工确认和持续评测。模型只是其中一部分，真正决定系统能不能落地的是整套工程边界。
